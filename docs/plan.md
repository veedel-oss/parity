# Plan

Working plan for the Rust implementation. Work on one or two steps per session, add tests, then tick the step off. Keep this file up to date after every step. Architecture and decisions live in `docs/architecture.md`.

Milestones 1 (end-to-end skeleton), 2 (comparison of packages), 3 (comparison of configuration directories) and 4 (comparison of the whole file system) are complete and removed; their decisions are in `docs/architecture.md`.

## Milestone 5: Release preparation

Steps 21 to 23 are complete; their decisions are in `docs/architecture.md` (Decisions, Command line, Builds) and `docs/security-review.md`. Steps 25 to 28 make sure that only the maintainer can publish a release. Steps 29 to 33 add a Debian package to the release, next to the plain binary.

- [ ] 24. First tagged release, 0.0.1.
  - Done: name (`parity`, not on crates.io), release notes in `CHANGELOG.md`, `.github/workflows/release.yml`.
  - Open: steps 29 to 33 first. Then, on the release commit, CI and e2e pass. The maintainer pushes the signed tag `v0.0.1`, approves the release job and publishes the draft release.
- [x] 25. Rulesets, setup GitHub Rulesets
- [x] 26. Repository and organisation settings, set by the maintainer: the maintainer is the only organisation owner, the base permission gives members no write access, nobody else has write, maintain or admin access to the repository, two-factor authentication is required, Actions allows only actions created by GitHub and requires full-length commit SHAs, the default `GITHUB_TOKEN` is read-only and cannot create or approve pull requests, workflows from fork pull requests of external contributors need approval, releases are immutable, and Dependabot alerts and security updates, Secret Protection (secret scanning and push protection) and private vulnerability reporting are enabled. The workflows fit these settings: only `actions/*`, each pinned to a full commit SHA, and write access only in the release job.
- [x] 27. `release.yml` in two jobs: a build job with read-only permissions and `persist-credentials: false`, and a release job with write permissions that runs no code of the project or its dependencies and creates the release as a draft. (Since the repository is public: the release job runs in the environment `release`, set up by the maintainer, and attests the build provenance of the binary with `actions/attest`. See `docs/architecture.md`, Builds.)
- [x] 28. Pin the Rust toolchain of the release build, so it changes only with a commit. (`rust-toolchain.toml`, for all builds, not only the release; see `docs/architecture.md`, Builds.)
- [x] 29. Debian package `parity_<version>_amd64.deb`, built with `cargo-deb` in the release only. CI and the e2e tests test the plain binary, and the package holds exactly those bytes. Configured in `[package.metadata.deb]` of `crates/parity/Cargo.toml`.
  - Built from the binary the build job already built and checked (`cargo deb -p parity --target x86_64-unknown-linux-musl --no-build --no-strip`), so cargo-deb neither rebuilds nor strips it (the release profile strips already).
  - Contents: `/usr/bin/parity` (0755), in `/usr/share/doc/parity/` the `copyright` (step 30) and the changelog from `CHANGELOG.md`, and the man pages and completions of step 31. `/usr/bin`, because a package must not install into `/usr/local`; it passes the holder's ownership checks and is on the SSH user's `PATH` and in sudo's `secure_path`, so `--parity-path` keeps its default. No maintainer scripts, conffiles, services or users: installing configures nothing, removing leaves nothing behind.
  - Fields: `Version:` the release version without a Debian revision (releases are immutable, a rebuilt package is a new tag anyway), `Section: admin`, `Priority: optional`, `Maintainer: veedel-oss <veedel-oss@mailbox.org>` (the project address from `SECURITY.md`), and the description from `Cargo.toml` with a few lines more. `depends` empty instead of cargo-deb's `$auto` (static binary), and no `Recommends`: the workstation needs an ssh client, a target an SSH server and sudo or su, and one package for both roles cannot say which.
  - Compressed with xz, cargo-deb's default, set explicitly: dpkg before 1.21.18 (Debian 10 and 11) cannot unpack zstd. `SOURCE_DATE_EPOCH` is the time of the tagged commit, so the file times in the package do not depend on when it was built.
- [ ] 30. `packaging/deb/copyright` (cargo-deb's `license-file`) in Debian's machine-readable format: Parity under AGPL-3.0-or-later with the full license text (`/usr/share/common-licenses` has no AGPL), and every crate linked into the binary and the musl of Rust's target, with copyright holders and licenses, whose MIT and Apache-2.0 terms ask for the notices to come with the binary. CI checks the file, not the package: it fails if a crate from `cargo tree --target x86_64-unknown-linux-musl -e normal,no-proc-macro` is missing there, so a Dependabot update that brings in a new crate cannot slip through.
- [ ] 31. Man pages and shell completions, generated in the release by `crates/xtask` (`publish = false`), a workspace tool that is never shipped: the binary, its dependencies and its commands stay as they are. `cargo run -p xtask -- gen-docs OUTDIR` renders the CLI's clap definition (`parity-analyze` exposes its `clap::Command`) with `clap_mangen` and `clap_complete`: `parity.1` and one page per command (`parity-compare.1`, `parity-packages.1`, `parity-ping.1`), and completions for bash, zsh and fish. They come from the help texts, so they stay in step with them, and `collect` and `hold`, which are not part of the clap definition, appear in neither. The package installs them in `/usr/share/man/man1/`, `/usr/share/bash-completion/completions/parity`, `/usr/share/zsh/vendor-completions/_parity` and `/usr/share/fish/vendor_completions.d/parity.fish`; the plain binary comes without them. A unit test of the generator checks that every option of every command appears in its man page and in each completion.
- [ ] 32. `release.yml`: the build job installs cargo-deb at a pinned version (`cargo install cargo-deb --version <x> --locked`, updated by hand, Dependabot does not see a version in a `run` line), runs the generator of step 31 into `target/deb-assets/`, builds the package from the checked binary and checks that its version matches the tag, its payload is xz and the binary in it is byte-identical to the released one. cargo-deb and its dependencies run in the build job, which has read access only. The release job attests the build provenance of both files, lists both in `SHA256SUMS` and attaches both to the draft. It still runs no code of the project.
- [ ] 33. Docs: an Installation section in the README (the package with `sudo apt install ./parity_<version>_amd64.deb` on Debian and its derivatives, with man pages and completions, the plain binary in `/usr/local/bin` elsewhere, on the workstation and on every target) replacing "not usable yet" under Status; `SECURITY.md` (Verifying a release) for the package too; `CHANGELOG.md` 0.0.1 names the package; `CONTRIBUTING.md` says that the package is built in the release only and how to build it locally with the generator; `AGENTS.md` (Workspace layout) names `crates/xtask` as a release tool that is not linked into `parity`. When the milestone is done: `docs/architecture.md` Decisions (Name and distribution: releases are the static binary and the Debian package on GitHub) and Builds (the package, built in the release only from the tested binary, and the generated man pages and completions).

## Later

- Package collection for more distributions beyond Debian.
- Map UIDs and GIDs to names in the CLI from the collected `/etc/passwd` and `/etc/group`, so system users with different UIDs on two machines do not show up as differences.
- Comparison against a saved snapshot instead of two live machines.
- Export of differences as Ansible or Terraform code.
- Smarter hashing on very large file systems (hash only files whose size matches on both sides, or in a second pass).
- aarch64: build it, run the e2e tests on an arm runner, then release it, as a binary and as an arm64 package.
- An APT repository, so that targets get new versions with `apt upgrade`. It needs a key that signs the repository's `Release` file, which the project does not have (releases are checked with `SHA256SUMS` and the attestation), and a place to host it.

## Open questions

- Whether the plain release binary should come with the license notices of the linked crates too, for example the package's `copyright` file as a release asset.

- Whether the CLI may copy the binary to the target for one run, or the binary must be installed beforehand.
- Whether the matching of path patterns for sensitive paths and excludes (`*` within one component, `crates/parity-collect/src/pattern.rs`) should also come from a well-known library such as `globset`, following the rule in `AGENTS.md` that security-relevant algorithms are never our own. It is the last such piece written here; against it speaks the size of that dependency in collect mode, which runs as root.
